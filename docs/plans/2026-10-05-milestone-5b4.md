# Milestone 5b4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the compiler side of `varyk-http`: when a build holds the package named `varyk-http`, its `App`'s route and hook calls are intrinsics that `varyk check` checks against each handler's signature and the backend compiles into one small adapter per route, plus the status on `Error`, two facade shapes, and `varyk add http sql`.

**Architecture:** The resolver finds `varyk-http` in the package graph and marks its `App`, `Request`, and `Response`. The type checker treats `App::new` and the route and hook calls on a marked app as a new `Owner::App` with an intrinsic table, checks paths, handlers, bindings, and return shapes, and records route and hook nodes in the HIR. Borrow analysis treats them as `mut self` uses. The backend writes a numbered adapter per node that calls the package's contract items (spec 4 and 6.1). A stub `varyk-http` fixture with no axum proves it all offline and end to end.

**Tech Stack:** Rust stable, edition 2024, MSRV 1.85. No new dependency in `varyk` or `varyk-std`. The stub fixture depends on `varyk-std` only.

**Spec:** `docs/specs/2026-10-05-milestone-5b4-design.md` ("spec 2.2" refers to its sections; "M5b3 §n" and the like to earlier specs). Read the spec before any task; it is the authority where this plan is brief.

## Global Constraints

- `AGENTS.md` applies in full: the gate after every task, MSRV 1.85 with no let-chains, minimum viable, fail loudly, stable codes with a fixture and a `docs/language.md` row, snapshots reviewed, conventional commits, safe by default. Before any push, `rustup run 1.85 cargo build --workspace` passes.
- New codes exactly: V0219 (route and handler do not fit), V0220 (handler or hook of the wrong shape), V0221 (route or hook call on an app that is not a local bound to `App::new` here, in a loop, or after the local is assigned again), V0222 (invalid path or prefix, or a route already taken), V0407 (this `varyk-http` does not match this compiler). Reused codes are those of spec 8. Headlines in plain words; Rust words only in notes.
- Spec 2.10 is the cut list; implement nothing on it. No `unwrap`, `expect`, or other crash-on-absence call in non-test code, the stub fixture's Rust included.
- The program's generated crate never names axum, tower, or reqwest; it names only `::<key>::` items of the package (spec 4, 6.1).
- Generated names use the reserved `varyk_` prefix only: `varyk_route_N` per module (one counter for routes and hooks), `varyk_req`, `varyk_res`, `varyk_N`.
- Every fixture or example manifest with a `varyk-std` line gets an `extra-files` entry in `release-please-config.json` in the same task that adds it.
- No attribution lines in commits or pull requests.

## Review Focus

Inputs the spec implies but no listed test would otherwise exercise, most likely to bite first. Each has a test in the task that owns the code.

1. A handler parameter named `req` or `state` compiles and binds correctly, since adapters use only `varyk_` names for their own locals. Task 6.
2. A `string` path parameter and an `Option<string>` query parameter are lent as `&str`-compatible and `&Option<String>` without a V0900; a `bool` query parameter is passed by value. Task 6.
3. A route registered in an `if` branch (not a loop) is accepted and registers once, while the same route in both branches of one `if` is V0222. Task 5.
4. A `before` hook registered after the route it must cover runs for that route through `app.request`. Task 7.
5. A program with routes and no `log::` call starts logging in `main` and in an async `#[test]`, so a 500's message reaches stderr. Task 8.

## Overview

Eight tasks. Tasks 1 to 3 are independent groundwork: the status on `Error` with the bare `varyk_std::Error` return (task 1), the `&T: Serialize + ?Sized` parameter shape (task 2), and `varyk add` with several official packages (task 3). Task 4 adds the stub `varyk-http` fixture, finds it in the graph, and makes `App::new` an intrinsic with V0221 and V0407. Task 5 checks route calls (V0219, V0220, V0222) and records route nodes. Task 6 generates route adapters and runs the first end-to-end program. Task 7 adds the three hooks. Task 8 adds logging in tests, the soundness templates, the remaining fixtures, and every document.

## Development Approach

- TDD per task: a failing test first, the minimal code, then the task's gate. Unit tests beside the code; fixtures, snapshots, and integration tests under `crates/varyk/tests/`.
- Each new code lands in the task that first produces it, with its fixture under `tests/fixtures/errors/v<code>_<case>/`, its registration in `tests/errors.rs`, its `codes.rs` entry in `ALL`, and its `docs/language.md` row, since the reference test needs a row for every code.
- The stub `varyk-http` (task 4) is the one package every later test uses. It lives at `tests/fixtures/packages/varyk-http/`, its crate name is `varyk-http`, it depends on `varyk-std` only (JSON through `varyk_std::json` and the `varyk_std::serde` re-export, no `serde_json`), and its facade implements the contract of spec 6.1 and the Varyk surface of spec 6.2 over an in-memory router with no network.
- Single-file test paths (`tests/codegen.rs`, `types/check/tests.rs`, plain error fixtures) see no package graph, and `Graph::for_tests` is crate-internal, so every test of an HTTP program goes through one of three mechanisms, all created in task 4:
  - **type tests:** a `varyk_http()` build in `src/test_packages.rs`, following `units_and_route` (~160), that adds the stub from `tests/fixtures/packages/varyk-http` (a `Build::add` variant taking a directory, since `add` reads `tests/fixtures/resolve/packages/`) with `varyk_std` as a Rust dependency; route and hook type tests live in `types/check/tests.rs` (beside `mod packages` ~5275) and use `Build::check` with `("http", Dep::Package("varyk-http"))`;
  - **error fixtures:** an `http_error_case!` macro in `tests/errors.rs` whose copy helper makes one fresh parent per call holding `<case>/` and `varyk-http/`, as `package_copy` does (`tests/common/mod.rs` ~139), and replaces that parent with `[dir]` in the snapshot, so parallel cases never share a half-copied stub; a case's manifest names `http = { path = "../varyk-http", package = "varyk-http" }`; one stub, one `extra-files` entry;
  - **generated Rust:** snapshots of the generated files of a built copy of the `http_user` package, following `trip_runs_with_route_s_log_line` (`tests/examples.rs` ~1003), not `tests/fixtures/codegen/`; route soundness templates are `MUST_RUN_TREES` entries (`tests/soundness.rs` ~2905) carrying the stub's files through `include_str!`.
- The route table follows the `Shared` and `Task` patterns: a builtin owner for the type's calls (`Owner::Shared` in `values.rs`), and per-function local tracking for where a value may be used (`task_local` in `asyncs.rs`).
- Adapter Rust follows `started_call`: bound values are named `varyk_N` and lent by the handler's parameter modes.
- Codegen snapshots of programs without the stub (tasks 1 and 2) are `insta` snapshots on fixtures under `tests/fixtures/codegen/`, as today. Regenerate only the snapshots a task means to change, and read every new `.snap`.
- Not needed: any axum, tower, or reqwest code in this repository; any runtime behaviour beyond what the stub needs to answer `app.request` (the real package has its own spec and repository).
