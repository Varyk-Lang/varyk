# Milestone 2 Implementation Plan

**Goal:** Extend the `varyk` compiler so the six milestone-2 examples check, build, and run: enums, `match`, `for`, methods, `Option`/`Result`/`Vec`, `?`, `format!`, `vec!`, `s.clone()`, `usize`, module type paths, and the alias soundness rule.

**Architecture:** The milestone-1 pipeline is unchanged (lexer, parser, resolver, type checker producing HIR, borrow analysis, Rust backend, cargo driver). Each new construct is added as a vertical slice through the type checker, borrow analysis, and backend once the syntax and the type representation are in place, so every task ends with programs that check and, where the backend is touched, build. Two internal changes come first because everything else builds on them: the backend stops re-deriving string representations, and the alias rule becomes a general liveness check.

**Tech Stack:** Rust stable, edition 2024, MSRV 1.85. No new dependencies: `clap`, `syn`, `quote`, `annotate-snippets`, `serde_json`, dev `insta`, as in milestone 1.

**Spec:** `docs/specs/2026-09-25-milestone-2-design.md`. The plan argues from it; section numbers below ("spec 3.1") refer to it, and "M1 §n" to `docs/specs/2026-09-23-varyk-design.md`. Read both.

## Global Constraints

- Milestone 2 is an MVP (spec 1). Only what the spec lists is supported; anything else gets a diagnostic naming the construct, never a panic or a silent mis-compile.
- No `todo!()` or `unimplemented!()` on any path the six examples exercise. No `unsafe` anywhere.
- `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` pass at the end of every task.
- Generated Rust stays readable and deterministic; builds never depend on rustfmt.
- The generated crate has no dependencies; copied `.rs` modules may use only the standard library.
- A diagnostic code is never reused for a different meaning. New codes: V0204, V0205, V0206, V0207, V0307. Widened codes: V0100, V0101, V0103, V0105, V0109, V0200, V0201, V0203, V0301, V0303; V0304 reworded (spec 6).
- Every new or widened diagnostic is written in plain words, says what to change, and puts the Rust term in a note (M1 §6.6).
- Test fixtures live under `crates/varyk/tests/fixtures/<case>/`, never named `main.rs`. Integration tests spawn the binary through `common::varyk` from the workspace root. New `insta` snapshots are created with `INSTA_UPDATE=always`, reviewed, and committed.
- Every "passes check, fails in rustc" bug found during the milestone extends the soundness templates in `crates/varyk/tests/soundness.rs`, not just the one case (spec 7).
- `docs/language.md` is updated in the same task as each surface addition.

## Review Focus

Inputs the spec implies but no example exercises, most likely to bite a person first. Each has a test pinned to the task that owns the code.

1. An owned `Option<Task>` local matched and its `Task` pushed into a `Vec`: V0304 must say to match on the call that produced it (spec 3.4). Task 8.
2. `for x in v { v.push(1); }` with `x` unused: V0307 must fire, pointing at the push and explaining the loop holds `v` (spec 3.1). Task 9.
3. `let v = Vec::new();` with no annotation: V0207 must show `let v: Vec<i32> = Vec::new();` as the shape, not a bare "cannot infer" (spec 2.6). Task 7.
4. A pattern binding that shadows an outer local of the same name, then the outer name used after the `match`: the outer local is intact, the binding is gone (scoping as `let`). Task 8.
5. `v.push(v.len())`: rejected by the existing V0306 although rustc accepts it; the message must name the receiver and suggest a `let` first, so the over-strictness reads as a rule, not a bug (spec 2.5, "an argument like any other"). Task 7.

## Overview

Milestone 2 adds the language core the spec describes and closes the alias soundness gap left by milestone 1. The work is eleven tasks in pipeline order. Tasks 1 and 2 are internal: the representation refactor and the alias rule, both from the milestone-1 follow-ups. Tasks 3 and 4 extend `varyk-syntax` with every new token, keyword, item, statement, expression, and pattern, each rejected construct getting its V0001. Task 5 changes `Ty` and the resolver so enums, `impl` blocks, generic standard types, `usize`, and module type paths exist as names. Tasks 6 through 10 are vertical slices, one per construct family, each touching the checker, borrow analysis, and backend and ending with programs that build: values and constructors, methods and the built-in table, `match`, `for`, and `?`. Task 11 adds the six examples, the integration tests, and the documentation the definition of done requires.

## Development Approach

- TDD per task: failing test first, minimal code, then the task's gate command. Unit tests next to the code; snapshots and integration tests under `crates/varyk/tests/`.
- Vertical slices from task 6 on: each construct lands in the checker, borrow analysis, and backend together, with a codegen snapshot and soundness templates, so it is exercisable through `varyk build` at the end of the task.
- Diagnostics-first: every new code gets a fixture under `tests/fixtures/errors/<code>_<case>/` and a rendered snapshot through `tests/errors.rs`, following the existing one-case-per-code pattern; widened codes get unit tests in the pass that emits them.
- Soundness templates follow the existing `soundness.rs` shape: a value kind put into a context kind, batched into one must-build program and one must-reject set. Every task from 6 on adds its value kinds (variant values, match bindings, `for` variables, index places, `?` results) and context kinds (payloads, `push`, index assignment).
- Backend follows the type-driven rule of M1 §6.3 and `bridge` in `rust_expr.rs`: compute what an expression has and what the context needs, and insert `&`, `&*`, `*`, or `.to_string()` to bridge. Never a case list per construct.
- Not needed and why: interning of `Ty` (spec 5 says clone), a pattern-usefulness algorithm (patterns are one level deep, spec 2.3), lifetime emission (borrowed returns are deferred, spec 3.3), anything on the "Not in milestone 2" list (spec 2.12).
