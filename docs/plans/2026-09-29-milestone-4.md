# Milestone 4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make everyday service code short: closures on iterator chains, `if let` and `while let`, patterns more than one level deep and on numbers and strings, the useful `Option`, `Result`, `Vec`, `string`, and `HashMap` calls, `as`, `.clone()` and `==` on structs and enums, and functions that return part of what they borrow without a copy.

**Architecture:** The pipeline is unchanged (lexer, parser, resolver, type checker producing HIR, borrow analysis, Rust backend, cargo driver). Two internal changes carry most of the milestone: the built-in table in `builtins.rs` grows a result kind per row (a plain value, a borrowed part of the receiver, an `Option` to look into, or a chain) and a closure parameter shape, so every new call is a data row the three later passes already know how to read; and borrow analysis gains a pre-pass that classifies every function's return as new or part of one parameter, which the call-site alias rule, the chain item kinds, and the closure-body rule all reuse. The language work lands in pipeline order, then the examples and docs.

**Tech Stack:** Rust stable, edition 2024, MSRV 1.85. No new dependencies. Existing: `clap`, `syn` (full), `quote`, `toml`, `annotate-snippets`, `serde_json`, dev `insta`.

**Spec:** `docs/specs/2026-09-29-milestone-4-design.md`. The plan argues from it; "spec 3.1" refers to its sections, "M1 §n", "M2 §n", and "M3 §n" to the earlier specs. Read all four.

## Global Constraints

- `AGENTS.md` applies in full: the gate at the end of every task, MSRV 1.85 with no let-chains, minimum viable, fail loudly, no hidden allocation, stable codes with a fixture and a `docs/language.md` line per new code, snapshots as reviewed content, conventional commit prefixes. It is not repeated here. Before any push, `rustup run 1.85 cargo build --workspace` passes.
- Milestone 4 is an MVP (spec 1). Section 2.13 of the spec is the cut list; do not implement anything on it. `unwrap` and `expect` are never added, in this or any milestone (spec 2.7).
- Every row of the spec 2.7 tables is used by an example of spec 4; a row no example uses is not added.
- Closures exist only as the argument of a table row whose parameter is written as a closure, take exactly one untyped parameter, capture by shared borrow, and may not contain `return`, `break`, `continue`, or `?` (spec 2.2, 3.2).
- A chain is one expression from a source on a stored receiver (or a string literal, for `split`) to a terminal or a `for` head; no chain consumes its source (spec 2.3, 3.3).
- A borrowed return is inferred, never written, and rooted at exactly one read-only parameter; the call result is an alias of the argument (spec 3.1).
- The compiler inserts no allocation except a literal into an owned slot and an explicit `.clone()`; `.copied()` copies Copy values only (spec 3.3).

## Review Focus

Inputs the spec implies but no example exercises, most likely to bite a person first. Each has a test pinned to the task that owns the code.

1. `fn name(mut self) -> string { self.name }`: V0304 at the function ("make the parameter read-only or copy the value"), never rustc's E0502 at a caller (spec 3.1). Task 7, plus a must-reject template.
2. `for w in words.iter().filter(|w| seen.contains(w)) { seen.push(w.clone()); }`: V0307 at the `push`, naming `seen` as read by the loop's head, never E0502 (spec 3.3). Task 11, plus a must-reject template.
3. `match owned { "admin" => "Administrator", other => other.clone() }` on an owned `string` local, stored into a `string`: builds, with the head written `.as_str()` and `other` a `&str` (spec 2.5, 3.5). Task 3, plus a must-build template.
4. `let n: i32 = text.parse().ok_or("bad")?;` in a function returning `Result`: V0207 whose message shows the two-statement form, not a type mismatch deep in `ok_or` (spec 2.7). Task 5 owns the message; task 6, where `ok_or` exists, owns the fixture.
5. `let f = |x| x + 1;` and `numbers.iter().map(|x| x).collect()` with items borrowed: V0001 naming the calls that take a closure (task 9), and V0304 naming `numbers` with the `.map(|x| x.clone())` hint (task 10) (spec 2.2, 3.3).

## Overview

Thirteen tasks in pipeline order. Task 1 moves the pattern parser and the owned-slot check into files of their own, with no behavior change, because both grow in this milestone. Task 2 extends `varyk-syntax` with every new token and construct and leaves the compiler rejecting the new AST nodes with V0001 until their tasks land. Task 3 delivers patterns: named-field variants, nested, literal, and range patterns, the usefulness check, `if let`, and `while let`. Task 4 delivers the small expression additions: `?` on `Option` with expected types through `?`, `as`, and `..=` in `for`. Task 5 adds the table rows whose result is a plain value and the `HashMap` type. Task 6 adds the rows that use up their receiver or are looked into where they are made, with the `rooted` field on method calls. Task 7 delivers borrowed returns and `trim`. Task 8 imports borrowed returns from Rust. Task 9 delivers closures, their captures, and `Option::map` and `map_err`. Task 10 delivers chains through their terminals, `split` included. Task 11 delivers `for` over a chain. Task 12 delivers derived `Clone` and `PartialEq`, `.clone()` and `==` on structs and enums, and derive reading in interop. Task 13 adds the six examples, the example edits, the soundness sweep, the reference-coverage test, and the documentation.

## Development Approach

- TDD per task: failing test first, minimal code, then the task's gate command. Unit tests next to the code; snapshots and integration tests under `crates/varyk/tests/`.
- Diagnostics-first: every new code gets a fixture under `tests/fixtures/errors/v<code>_<case>/` and a rendered snapshot through `tests/errors.rs`; every widened code gets at least one new fixture for its new case and a unit test in the pass that emits it.
- Table rows are data: a new call is a `Builtin` row plus a soundness template plus a reference line, never a special case in the checker or backend. The three passes read the row's receiver mode, shapes, and result kind (task 5).
- One classification function: the return classification of task 7 (new, part of one parameter, error) is written once in `borrow/returns.rs` and reused for closure bodies in tasks 9 (`Option::map`, `map_err`) and 10 (chain `map`). Two root notions, kept apart as the code keeps them: the syntactic roots of a place (`borrow.rs::roots` and `place_root`, fed into `refers` by `bind` and `borrow/patterns.rs`), and the flow closure over them (`borrow/aliases.rs::alias_roots`), which stays the only flow computation.
- Soundness templates follow the existing shape in `soundness.rs`: a function body snippet in `MUST_PASS`, or a body with its Varyk code and rustc code in `MUST_REJECT`, each wrapped by `function()` with the fixed `PARAMS`, `SETUP`, and `EPILOGUE`; `PRELUDE` grows the helper items a task needs (a struct with a getter, a `HashMap` maker, a derived type), and multi-file cases such as an `ext.rs` with derives go in the `_TREES` lists. Every reviewer-found "passes check, fails rustc" program from the spec's review rounds (spec 7) lands in `MUST_REJECT` in the task that owns it.
- Backend output goes through the type-driven bridging in `rust_expr.rs` (`Have`, `Need`, `bridge`); a new emission adds a `Have` or `Need` case rather than a string special case, except the four the spec names: `.copied()`, `.as_str()` heads, `contains` on a `Vec<string>`, and the `Ok::<T, E>` turbofish.
- Two place notions, kept apart: `hir::is_place` stays the syntactic test the checker uses (assignment targets, `match` heads) and does not change meaning; a call whose result borrows from one argument carries `rooted: Option<usize>` on its HIR node (set by the checker for table rows, tasks 6 and 7, except `find`, whose looked-into status `chains.rs` records as `looked_into`, task 10, and by return classification for functions, tasks 7 and 8), and the context-free borrow and backend helpers read it, so no helper needs the program passed in.
- Closure state lives in borrow analysis, not in HIR locals: HIR marks a closure's parameter as `LocalKind::ClosureParam` and lists the closure's captures; whether a use is inside a closure is decided by position against a stack of closure body spans, whether a local may be given away is a borrow-side table keyed by `LocalId`, and the kind of a chain item one keyed by chain call; the exceptions are `ClosureParam { deref }` and `looked_into`, which borrow analysis writes into HIR as it writes `repr`, because the backend reads only HIR.
- Generated code never lets a compiler-chosen name capture a user expression: when the backend introduces a closure or binding of its own, every user expression it mentions is evaluated into a compiler-chosen name first (the `contains` rewrite of task 5 is the one case today); any new rewrite that needs a name follows it and gets a run test with a user local of the same name.
- Each task that replaces a task-2 stopgap deletes that stopgap and its fixture or snapshot in the same task.
- Not needed and why: reading `std` signatures (spec 2.7, the table is the declaration), function types or closure values (spec 2.2), owned items at a chain's source or `into_iter` (spec 3.3), `is_some()` on a looked-into result (spec 2.8), `Debug` derives (spec 2.13), `HashMap` in `.rs` signatures (spec 2.13), a fixed-point over the call graph (spec 3.1 uses strongly connected components once), and anything in spec 2.13.
