# Milestone 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `varyk` compiler that checks, builds, and runs the six milestone-1 examples by generating a Cargo project and invoking cargo.

**Architecture:** Two crates. `varyk-syntax` holds spans, tokens, lexer, parser, and AST with no semantics. `varyk` holds diagnostics, resolver, type checker, borrow analysis, HIR, the `syn`-based import of `.rs` signatures, the `Backend` trait with `RustBackend`, the cargo driver, and the CLI. Every stage up to HIR is testable without cargo.

**Tech Stack:** Rust stable, edition 2024. Dependencies: `clap` (CLI), `syn` with the `full` feature and `quote` for its `ToTokens` trait (Rust signature import and signature text), `annotate-snippets` (diagnostic rendering; pin the latest release and read its README, since its API has changed across minor versions), `serde_json` (JSON diagnostics through its `json!` macro). Dev dependency: `insta` (snapshots). No other crates.

**Spec:** `docs/specs/2026-09-23-varyk-design.md`. The plan argues from the spec; read both. Section numbers below refer to it.

## Global Constraints

- Milestone 1 is an MVP (spec section 4 intro). Nothing beyond the six examples and the diagnostics listed in section 6.6 is in scope. When in doubt, emit an "unsupported" diagnostic rather than implement.
- No `todo!()` or `unimplemented!()` on any path the six examples exercise. No `unsafe` anywhere.
- `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --check` pass at the end of every task.
- The generated Rust must be readable and deterministic. Builds must not depend on rustfmt.
- Only the standard library may be used in copied `.rs` modules; the generated crate has no dependencies.
- Test fixtures (erroneous `.vr` programs and helper `.rs` files) live under `crates/varyk/tests/fixtures/<case>/` and are never named `main.rs`, so cargo does not discover them as test targets.
- Integration tests spawn the compiled binary through `env!("CARGO_BIN_EXE_varyk")` with the working directory set to the workspace root, because `cargo test -p varyk` runs with the crate directory as its working directory.
- Snapshot tests use `insta` without `cargo-insta`: the first run of a new snapshot uses `INSTA_UPDATE=always`, the resulting `.snap` files are reviewed and committed, and later runs use the plain gate command.

**Diagnostic codes.** Every diagnostic carries one of these codes. Syntax codes are defined in `varyk-syntax`; the `varyk` crate re-exports them from its registry next to the semantic ones. A code is never reused.

## Overview

The compiler is a straight pipeline: lexer, parser, resolver (which also loads modules and imports Rust signatures), type checker producing HIR, borrow analysis annotating the HIR, and a Rust backend that writes a Cargo project which the driver builds. The plan builds it front to back, wiring `varyk check` as soon as the parser exists and extending it in every semantic task, so every diagnostic is reachable from the command line as soon as it exists. The last tasks add the backend, the driver, the six-example integration tests, and the documentation the definition of done requires.

Two deliberate simplifications from the spec's file list: the type checker builds the HIR directly instead of producing a separate typed AST, and string representation inference lives in `borrow.rs` next to the place analysis it depends on, rather than in `types.rs`. Task 1 updates the spec and roadmap wording to match.

## Development Approach

- TDD per task: write the failing test first, make it pass, then run the task's gate command. Unit tests live next to the code in each module; snapshot and integration tests live in `crates/varyk/tests/`.
- Diagnostics-first: every error path listed in section 6.6 gets a test asserting the code and the span, and a rendered snapshot for the human format in Task 14.
- Follow rustc's conventions for the pieces that mirror it: byte-offset spans with a line index, a Pratt parser for expressions, a HIR that records decisions rather than syntax.
- No parser error recovery: the parser stops at the first V0002 in a file. Only the three Rust-habit diagnostics (V0010 to V0012) report and continue, as spec section 6.3 requires. Whenever the parser would emit V0002 on a `ReservedKeyword` token, it emits V0001 naming the keyword instead.
- No spans inside `.rs` files: a Rust module that does not parse is reported at the `mod` declaration that loaded it. A `.rs` module declaring a nested `mod` is not detected by Varyk; rustc rejects it and the error passes through per section 6.5.
- Single-file programs never touch disk: every stage takes a `SourceFile`, and only `mod` declarations cause file reads, so unit tests build programs from strings.
- Every milestone-1 diagnostic is an error; there is no severity type. String literals keep their raw text from lexer to generated Rust, since Varyk's five escapes are valid Rust escapes.
- Literal typing is expected-type propagation only: a literal takes the type its context requires, otherwise the fallback. No unification variables, so `let x = 10; takes_i64(x)` is a type mismatch in milestone 1. Task 1 aligns spec section 4.1 with this.
- Not needed and why: no source maps or rustc error mapping (milestone 2, section 6.5); no cargo JSON parsing (the executable path is computed, section 6.4); no `.vr` nested modules or `mod.vr` directories; no methods, enums, generics, or `use` (section 4.6). Reject each with V0001.
- Commit after each task with a message naming the task.
