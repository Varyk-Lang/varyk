# Milestone 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a Varyk program a Cargo package: `Cargo.toml` with dependencies used through `.rs` facades, modules at any depth, `use`, private fields, Rust structs, methods, and enums imported from `.rs` modules, plain `cargo build` through `varyk init`'s `build.rs`, `varyk publish` producing a crate whose consumers need no `varyk`, and rustc errors reported at the Varyk line.

**Architecture:** The pipeline is unchanged (lexer, parser, resolver, type checker producing HIR, borrow analysis, Rust backend, cargo driver). Three internal changes come first because everything else builds on them: the backend writes through a line writer that records source spans and puts lint allows on items instead of the crate, one routine writes the generated tree to any directory, and three oversized files are split. Then the language work lands in pipeline order (syntax, module tree and visibility, `use`, field `pub`, Rust import), then the package work (manifest and package mode, Rust-layer error mapping, `init`/`emit`, `publish`), then examples and docs.

**Tech Stack:** Rust stable, edition 2024, MSRV 1.85. One new dependency, `toml = "1"` (its 1.1.x line declares `rust-version = 1.85`). Existing: `clap`, `syn` (full), `quote`, `annotate-snippets`, `serde_json`, dev `insta`.

**Spec:** `docs/specs/2026-09-26-milestone-3-design.md`. The plan argues from it; "spec 2.3" refers to its sections, "M1 §n" and "M2 §n" to the milestone-1 and milestone-2 specs. Read all three.

## Global Constraints

- Varyk code never names a crate. `use` accepts only `crate::`, `self::`, `super::`, and modules declared in the same file (spec 3.3).
- Visibility is one rule for modules, items, and fields (spec 3.2). No `pub(crate)`, no `pub(super)`.

## Overview

Fourteen tasks in pipeline order. Task 1 splits `driver.rs`, `resolve.rs`, and `interop.rs` into directories with no behavior change. Task 2 rebuilds the backend's output path: a line writer that records spans, item-level lint allows, nested file paths, and the routine that writes the tree to a directory. Task 3 extends `varyk-syntax` with `pub mod`, `use`, field `pub`, and paths of any length. Task 4 gives the resolver a module tree of any depth and path resolution with `crate::`/`self::`/`super::`. Task 5 adds the visibility rule. Task 6 adds `use`. Task 7 adds field-level `pub`. Tasks 8 and 9 extend the Rust importer to structs with methods and to enums, with imported types in signatures. Task 10 adds `package.rs`, the manifest diagnostics, and package mode in the CLI and driver. Task 11 maps rustc messages to Varyk lines and passes `.rs` messages through. Task 12 adds `emit` and `init`. Task 13 adds `publish`. Task 14 adds the three example packages, soundness templates, and documentation.

## Development Approach

- TDD per task: failing test first, minimal code, then the task's gate command. Unit tests next to the code; snapshots and integration tests under `crates/varyk/tests/`.
- Diagnostics-first: every new code gets a fixture under `tests/fixtures/errors/<code>_<case>/` and a rendered snapshot through `tests/errors.rs`, following the one-case-per-code pattern; widened codes get unit tests in the pass that emits them.
- Package fixtures follow one shape: `tests/fixtures/packages/<case>/` holding `Cargo.toml`, `src/`, and, where a dependency is needed, `dep/` with a two-line Rust crate referenced by `path = "dep"`. A `common::package_dir(case)` helper copies a fixture into `CARGO_TARGET_TMPDIR` so tests never write into the source tree.
- Visibility follows one function in `resolve/visibility.rs`, called from every lookup; no lookup re-implements the rule (spec 3.2). Imported structs and enums go into the same `StructDef`/`EnumDef` tables with an `imported` flag, so the checker, borrow analysis, and backend take the existing paths (spec 8).
- Backend output goes through the line writer of task 2 from then on: every emitter that writes a line names the span it came from. Never `format!` a multi-line string into the output directly.
- Soundness templates follow the existing shape and gain a second module file per case where needed (nested modules, imported types), by extending `write_program` to take a list of files.
- Not needed and why: a separate Varyk manifest (M1 §6.8), `cargo metadata` (check is cargo-free, spec 2.2), a `syn` tree walk over nested `.rs` modules (cut, spec 6), `#[path]` in emitted `mod` lines (the tree mirrors the source, spec 3.1), column-level source maps (line-level is what rustc's line numbers need, spec 5), merging into an existing project in `init` (cut, spec 2.5), anything in spec 6.
